# GQA 优化优先级

先读本文件，再读 `source.json` 和 CANN FlashAttentionScore 材料。题目定义与固定评测规范决定语义和验收标准。以下建议用于安排实验顺序，每项改动都需要独立验证。

## 最高优先级：保留稳定 softmax

每行先计算 FP32 最大值，再计算 `exp(score - max)`、FP32 求和与归一化。因果区域外的概率必须为零；对齐补齐区不得参与有效元素的归约。

直接计算 `exp(score)` 即使通过固定随机输入，也可能溢出。同一题目 Shape/Dtype 下，Q 和 K 全取 16 时，缩放后的有效 score 约为 2896；去掉减最大值会产生非有限输出，稳定版本可以正常计算。因此不能把删除 ReduceMax 和减最大值当作有效的性能优化。

自定义归约要保留后续归一化所需的原始指数值。直接在概率缓冲上做 `Add(data, data, data[half], ...)` 会覆盖分子；另需正确处理非二次幂长度、尾块及归约后的同步。优先沿用已验证的 ReduceSum，再单独验证替代算法。

## 优先尝试：任务划分与中间数据搬运

- 区分 Cube 与 Vector 的任务数。当前分阶段设计可优先试验 24 个 Cube block、48 个 Vector block，并与 20/40 比较；block 数不等于同时驻留的物理核心数。
- 优先考察 query 行块 M=128。M=64、128、256 各有启动次数、UB 用量和搬运代价；较大的 M 并不必然更快。变更时同时核对 tiling、scratch 大小、pack/scatter 与因果边界。
- QK scores、概率和 PV 写回可分别试验 BF16 存储以减小 GM 读写；softmax 最大值、指数及求和保留 FP32。每次只调整一个精度边界，记录误差与耗时，避免把存储精度与累加精度混为一谈。
- PV 直接输出 BF16 可省去单独的 FP32→BF16 转换；收益可能很小，应结合重复测量判断。保持所有输出都被本次调用完整写入。
- 保留 Cube-only matmul 所需的 `ASCENDC_CUBE_ONLY` 定义及头文件顺序。核对 QK 转置、Q head 到 KV head 的 `h / 4` 映射、SetTensorA/B 偏移和当前调用方 stream。

## 有明确依赖后再优化同步

按 GM→UB、Vector 计算、UB→GM、Cube 输出的生产者与消费者逐段检查同步。删除 barrier 需要证明对应依赖已由其他同步覆盖。保留当前 stream 上完整的计算依赖；引入辅助 stream 时必须在返回前与调用方 stream 汇合。

双 stream、双缓冲和将多行块打包成 wave 会增加 scratch、调度和同步开销。已有候选没有显示必然收益。`depthA1/depthB1` 从 2 增至 4、增大 baseN、预缩放并重新量化 Q，也都需要分别检验资源约束与精度，不能当作默认优化。

分母与输出累加器必须一起重缩放。检查 UB/L1 容量、搬运对齐、尾块和 Cube/Vector 同步，再尝试流水重叠。

## 实验执行顺序与计时

1. 阅读本文件、题目和共同起始源码；保持源码不变运行 `python eval.py`，记录 version0。
2. 从稳定 softmax 出发，一次改变一个可解释因素；每次有效改动调用固定评测，记录版本、误差、绝对耗时及加速比。
3. 先考察 M、Cube/Vector 工作分配及中间存储，再尝试依赖明确的同步精简和融合。保留最佳正确源码的独立副本。
4. 当一个方向反复迭代没有成果、成果波动、成果收益很低，应该思考其他方向
